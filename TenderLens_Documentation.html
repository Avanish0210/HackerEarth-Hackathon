📌 Project Overview 📋 TenderLens 🔗 UBID Bridge

📌 Project Overview

This hackathon project combines two backend systems into a unified government digital transformation platform:

  • TenderLens — an AI-driven procurement evaluation engine that automates tender criteria extraction, bidder document parsing, and evaluation reporting.
  • UBID Bridge — a citizen data synchronization system that maintains consistent records across government departments using event-driven messaging, polling, and conflict resolution.

What is this project?

The project is a dual-backend solution for public sector modernization. It solves procurement inefficiencies and citizen data inconsistencies by providing two specialized backend systems working in parallel with a shared operational philosophy: automation, reliability, and auditability.

What must the frontend be?

The frontend should be a management dashboard that connects to both backend systems and offers:

  • Upload and review interfaces for tenders and bidder documents
  • Evaluation status, audit history, and manual review workflows for TenderLens
  • Event monitoring, conflict resolution, department registry, and audit feeds for UBID Bridge
  • Unified dashboards showing processing health, Kafka queue state, and data sync status
  • Role-based access for procurement officers, system administrators, and data stewards

Main thinking and logic

The main design idea is to split responsibilities cleanly:

  • TenderLens focuses on document intelligence: extract criteria, evaluate bidders, and optionally escalate uncertain results to humans.
  • UBID Bridge focuses on data consistency across departments: receive source system events, translate them, propagate them reliably, and detect/rescue conflicts.

Both backends are built with enterprise-grade patterns: message-driven processing, idempotency, audit logging, retries, and human-in-the-loop review when needed.

📋 TenderLens: AI-Powered Tender Evaluation

🎯 Mission: Transform government procurement from manual, error-prone processes to AI-driven, automated evaluation systems that ensure fairness, compliance, and efficiency.

🔍 What TenderLens Does

TenderLens is a sophisticated backend application designed to revolutionize the tender evaluation process in procurement systems. It automates the traditionally manual and time-consuming task of evaluating bidder submissions against predefined tender criteria. The system leverages cutting-edge AI technologies to extract, analyze, and evaluate tender documents with high accuracy and efficiency.

✨ Core Capabilities:

  • 📤 Tender Document Upload: Procurement officers upload tender requirement documents (PDFs)
  • 🤖 AI-Powered Criteria Extraction: Uses Large Language Models (LLMs) to automatically extract eligibility criteria from tender documents
  • 📄 Bidder Document Processing: Handles bidder submission documents with OCR capabilities for scanned PDFs
  • ⚖️ Automated Evaluation: Matches bidder qualifications against tender criteria using AI analysis
  • 👥 Human-in-the-Loop Review: Flags uncertain evaluations for manual officer review
  • ⚡ Asynchronous Processing: Handles large-scale evaluations efficiently using message queues
  • 📊 Audit Trail: Maintains complete logs of all evaluation decisions and processes

🎯 Problem Statement

❌ Current Challenges:
  • ⏰ Manual Labor Intensity: Procurement officers must manually review hundreds or thousands of pages of bidder documents
  • ⚖️ Human Error and Bias: Subjective evaluation can lead to inconsistent decisions and potential bias
  • 🕐 Time Consumption: Evaluation cycles can take weeks or months, delaying project timelines
  • 📈 Scalability Issues: Large tenders with many bidders become increasingly difficult to manage manually
  • 📋 Compliance Risks: Ensuring all criteria are properly evaluated and documented
  • 🔍 OCR Challenges: Many bidder documents are scanned PDFs requiring optical character recognition
✅ TenderLens Solution: Automates 80-90% of the evaluation process while maintaining human oversight for critical decisions, reducing evaluation time from weeks to days while improving accuracy and compliance.

🗄️ Database Architecture

Primary Database: PostgreSQL 16

TenderLens uses PostgreSQL as its primary relational database with a dedicated tenderlens schema. The database design follows these principles:

📊 Core Entities:

🏛️ Tender
Fields: id, tender_ref, title, uploaded_by, file_name, file_path, ocr_required, status, timestamps
Role: Stores tender document metadata and processing status
📋 Criterion
Fields: id, tender_id, criterion_ref, description, type, mandatory, threshold_value, operator, confidence, confirmed
Role: Defines evaluation criteria extracted from tender documents (financial, technical, compliance, certification)
🏢 Bidder
Fields: id, tender_id, bidder_ref, company_name, file_name, file_path, ocr_required, parse_status
Role: Represents bidder companies and their submission documents
⚖️ Evaluation
Fields: id, tender_id, bidder_id, criterion_id, extracted_value, source_doc, verdict, confidence_score
Role: Stores the results of matching bidders against criteria
🔍 ReviewQueue
Fields: id, evaluation_id, reason, priority, assigned_to, status
Role: Holds evaluations that require human review due to low AI confidence
📄 Report
Fields: id, tender_id, report_type, generated_at, file_path, status
Role: Generated evaluation reports and summaries
📝 TenderAuditLog
Fields: id, tender_id, action, user_id, timestamp, details
Role: Complete audit trail of all system actions

🔗 UBID Bridge: Citizen Data Synchronization

🎯 Mission: Create a unified, real-time data synchronization platform that ensures citizen information remains consistent across all government departments while preventing data conflicts and maintaining audit trails.

🔍 What UBID Bridge Does

UBID Bridge is a sophisticated event-driven data synchronization platform that acts as the central nervous system for citizen data management across government departments. It ensures that when a citizen's information changes in one system, it gets reliably propagated to all relevant departments while handling conflicts, maintaining data integrity, and providing complete audit trails.

✨ Core Capabilities:

  • 🎯 Unique Business Identifier (UBID): Centralized citizen identification system
  • 📡 Event-Driven Architecture: Real-time data synchronization using webhooks and polling
  • ⚖️ Conflict Resolution: Intelligent handling of conflicting data updates
  • 🔄 Bidirectional Sync: Data flows from SWS to departments and back
  • 🛡️ Idempotency: Prevents duplicate processing with Redis-based tracking
  • 📊 Audit Trail: Immutable logs of all data changes and propagations
  • 🔧 Multiple Integration Types: Webhook, polling, and snapshot-based synchronization

🎯 Problem Statement

❌ Current Challenges:
  • 🔀 Data Silos: Citizen data scattered across multiple department systems with no synchronization
  • ⚡ Real-time Updates: Changes in one department not reflected in others for days/weeks
  • 💥 Data Conflicts: Same citizen record updated simultaneously in different departments
  • 📋 Manual Reconciliation: Officers spend hours reconciling conflicting data
  • 🚫 No Audit Trail: Impossible to track who changed what and when
  • ⏰ Batch Processing: Updates happen in batches, not real-time
  • 🔍 Data Inconsistency: Different departments showing different information for same citizen
✅ UBID Bridge Solution: Real-time, event-driven synchronization with intelligent conflict resolution, ensuring all departments always have consistent, up-to-date citizen information.

🗄️ Database Architecture

Dual Schema Design: PostgreSQL 16

UBID Bridge uses PostgreSQL with two dedicated schemas for complete separation of concerns:

📊 UBID Schema Entities:

🏛️ Department Registry
Fields: id, ubid, department_id, department_name, integration_type, active, registered_at
Role: Maps which departments maintain records for each UBID
📝 Audit Log (Immutable)
Fields: id, event_id, ubid, source_system, target_system, event_type, field_changed, old_value, new_value, status, conflict_policy
Role: Append-only audit trail of all data propagations (never updated/deleted)
⚖️ Conflict Queue
Fields: id, event_id, ubid, field_name, source_a, value_a, source_b, value_b, resolution_policy, resolved, resolved_by, resolved_value
Role: Holds conflicting updates for manual resolution
📸 Department Snapshot
Fields: id, department_id, ubid, field_name, field_value, value_hash, snapshot_at
Role: Stores SHA-256 hashes for change detection in snapshot-based integrations
🔑 Idempotency Log
Fields: id, event_id, ubid, target_system, processed_at
Role: Prevents duplicate event processing (mirrors Redis for audit)

🚀 When UBID Bridge Backend is Running

1️⃣ SWS Citizen Update

State Welfare System detects citizen address change:

POST /api/ubid/events/sws Content-Type: application/json { "eventId": "evt-12345", "ubid": "UBID-001", "eventType": "ADDRESS_CHANGE", "fields": { "street": "123 MG Road", "city": "Varanasi", "state": "Uttar Pradesh", "pincode": "221001" }, "occurredAt": "2025-01-15T10:30:00Z", "initiatedBy": "welfare_officer" } Response: { "status": "ACCEPTED", "eventId": "evt-12345", "message": "Event received and queued for propagation" }

2️⃣ Registry Lookup & Translation

Bridge looks up which departments have records for UBID-001:

Registry Query Result: - DEPT_A (Revenue): WEBHOOK integration - DEPT_B (Transport): POLLING integration - DEPT_C (Education): SNAPSHOT integration Translation for Revenue Dept: { "ubid": "UBID-001", "address": { "house_number": "123", "street_name": "MG Road", "city_name": "Varanasi", "state_code": "UP", "postal_code": "221001" } }

3️⃣ Kafka Propagation

Tasks published to Kafka for each department:

Kafka Topic: ubid-propagation-tasks Key: UBID-001 (ensures ordered processing) Message 1: { "eventId": "evt-12345", "ubid": "UBID-001", "sourceSystem": "SWS", "targetSystem": "DEPT_A", "eventType": "ADDRESS_CHANGE", "payload": { "translated_address_data": "..." }, "retryCount": 0 } Message 2: { "eventId": "evt-12345", "ubid": "UBID-001", "sourceSystem": "SWS", "targetSystem": "DEPT_B", "eventType": "ADDRESS_CHANGE", "payload": { "translated_address_data": "..." }, "retryCount": 0 }

4️⃣ Department Updates

PropagationConsumer processes each task:

Processing Task for DEPT_A: POST http://localhost:8080/mock/dept-a/update { "ubid": "UBID-001", "address": { "house_number": "123", "street_name": "MG Road", "city_name": "Varanasi", "state_code": "UP", "postal_code": "221001" } } Response: 200 OK → Idempotency marked in Redis → Success audit log written → Manual acknowledgment sent to Kafka

5️⃣ Conflict Detection

If concurrent updates occur within conflict window:

Conflict Detected: - Source A: SWS (new address) - Source B: DEPT_A (different address update) - Field: address - Policy: LAST_WRITE_WINS Resolution: Accept SWS update (higher priority) Manual escalation if policy = MANUAL_ESCALATION

6️⃣ Bidirectional Sync (Polling)

Scheduled poller checks for department changes:

@Scheduled(cron = "0/60 * * * * *") // Every 60 seconds For POLLING departments: GET http://localhost:8080/mock/dept-b/snapshot Compare with previous snapshot: - Address changed for UBID-001 - Generate reverse event - Send back to SWS via same flow

7️⃣ Audit Trail

Audit Log Entries: { "eventId": "evt-12345", "ubid": "UBID-001", "sourceSystem": "SWS", "targetSystem": "DEPT_A", "eventType": "ADDRESS_CHANGE", "status": "SUCCESS", "oldValue": "old_address", "newValue": "123 MG Road, Varanasi", "createdAt": "2025-01-15T10:30:15Z" }
